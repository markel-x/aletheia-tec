# ADR-0014 · OID4VP 1.0 como verificador: perfil mínimo interoperable

- Estado: Aceptada · 2026-09-30 · Amplía ADR-0007 (la API propia de presentación se mantiene)

## Contexto
Hasta ahora la presentación llegaba por la API propia (`/v1/presentation-requests` +
`/v1/verifications`): el verificador tenía que conseguir la presentación del titular por su cuenta, así
que **ningún wallet estándar podía presentar a Aletheia**. OID4VP 1.0 es el protocolo que usan los
wallets (EUDI, HAIP) para eso.

## Decisión
Aletheia actúa como **verificador OID4VP 1.0** en el flujo entre dispositivos:

| Aspecto | Elección |
|---|---|
| Transporte de la solicitud | **Por valor** en `openid4vp://?…` (QR o enlace). Sin `request_uri`. |
| Identificador del cliente | Prefijo `redirect_uri:` con el `response_uri` (`client_id = redirect_uri:https://{host}/oid4vp/response`). La solicitud **no se firma** (§5.9.3). |
| Modo de respuesta | `direct_post` a `https://{host}/oid4vp/response` (formulario con `vp_token` y `state`). |
| Consulta | **DCQL** con una credencial `dc+sd-jwt`: `meta.vct_values` y `claims[].path`. Por defecto se derivan de la política (`accepted_vcts`, `required_claims`); se pueden indicar al crear la sesión. |
| `vp_token` | Objeto JSON `{"credential": ["<SD-JWT~…~KB-JWT>"]}` (formato de OID4VP 1.0). |
| Vinculación | KB-JWT con `aud = client_id` y `nonce` de la solicitud (un uso, 10 min, consumo atómico tras validar). |
| Validación | Las 11 comprobaciones existentes + comprobación `dcql`: cada claim pedido debe estar divulgado; si falta, `invalid` / `requested_claim_missing` y no se entregan claims. |
| Resultado | El backend del verificador consulta `GET /v1/oid4vp/requests/{id}`. El resultado con claims se guarda **cifrado** (envelope, como los claims pendientes) y se borra a los 10 minutos (ADR-0009). El registro de verificación sigue sin claims. |
| Rechazo del titular | `error` (p. ej. `access_denied`) + `state` → sesión `failed`. |

## Alternativas descartadas por ahora
- **`x509_san_dns` / `x509_hash` con solicitud firmada** (lo que exige HAIP y aceptan más wallets):
  requiere un certificado de verificador y su cadena. Mismo motivo que ADR-0004 para `x5c`.
- **`direct_post.jwt`** (respuesta cifrada al verificador): requiere claves de cifrado del verificador
  y `client_metadata.jwks`.
- **`request_uri`**: sólo aporta si la solicitud va firmada; por valor el QR es más denso pero cabe.
- **Mismo dispositivo** (`redirect_uri` de vuelta tras `direct_post`) y **varias credenciales** en una
  consulta.

## Consecuencias
- Un wallet que admita el prefijo `redirect_uri:` y DCQL puede presentar a Aletheia sin integración
  propia. **Muchos wallets de producción exigen solicitudes firmadas** (x509): con ellos este perfil no
  funcionará hasta implementar la alternativa anterior.
- Interoperabilidad comprobada sólo con `@sd-jwt/sd-jwt-vc` actuando de wallet (`interop/run.mjs`);
  **no con un wallet real**.
